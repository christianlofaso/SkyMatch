# Known constraints and gotchas

- **`ai.messages.create` is synchronous.** Always wrap in `asyncio.to_thread()` when running alongside other async work. Calling it directly in an `async def` blocks the entire event loop. In `/run`, connections and internships run in parallel via `asyncio.gather`, so a blocking Claude call in one branch freezes the other — `connections.py`'s Claude call is wrapped in `asyncio.to_thread` for exactly this reason (it had been a blocking call).

- **DDGS is synchronous and not thread-safe.** Each `asyncio.to_thread` call using DDGS must instantiate its own `DDGS()` object. Calling `DDGS().text()` directly in an `async def` blocks the event loop AND can hang for minutes when DDG rate-limits (common late in a `/run`, after the bucket scrapes already hit DDG). Reach URL-finding (`_find_job_url`, `_find_via_startup_boards`) runs its DDG work in a thread bounded by `asyncio.wait_for(timeout=_DDG_URL_TIMEOUT=15)` — on timeout the item gets no URL and is dropped downstream (graceful degradation).

- **Opus 4.8 rejects `temperature`/`top_p`/`top_k`** (400 `temperature is deprecated for this model`). All `MODEL_FULL` calls in `analyze.py` had `temperature` removed during the 4.5→4.8 migration; the Haiku quick-verdict call still passes `temperature` (Haiku accepts it). Do not add sampling params to Opus calls.

- **`max_tokens` truncation surfaces as "retry".** Opus 4.8 runs longer than 4.5, and a too-low `max_tokens` cuts the JSON mid-output → `json.loads` fails → the card shows a "retry" badge. In `analyze.py`: extraction is **2048** (was 1024 — Amazon's 18-requirement posting overflowed it), roadmap **4096**, evidence 2048. `internships.py` serving is zero-LLM; the only Claude call is the deferred `_annotate_fit_sync` behind `/internships/annotate`, which emits just `{fit_explanation, reach_gap}` (`max_tokens=160`; `fit_explanation` ~2 sentences / ~30 words, `reach_gap` ~25 words for a scannable shortlist + faster generation). If you add longer explanation text, bump the 160.
- **The internships annotation fan-out is input-token-heavy — mind the org's per-minute limits.** The fan-out no longer runs in `search_internships` (that path is zero-LLM) — it moved to `POST /internships/annotate`, which the results page fires *after* the feed paints, one small Claude call per served role (~up to 20 deduped URLs). On a low tier (e.g. 30k input-tokens/min, 50 req/min) the burst grazes the limit. Two guards keep it working and must stay: (1) `_profile_brief(profile)` sends a terse profile, NOT `model_dump(indent=2)` — the full dump re-sent per role blows the input-TPM limit; (2) the shared client is `anthropic.Anthropic(max_retries=…)` so 429s recover (slower) instead of dropping roles. In-flight calls are bounded by the global `sonnet_slot()` governor (Redis-distributed when `REDIS_URL` is set, per-process otherwise); if you re-add big per-call input, re-check against the tier limits.

- **Mojibake repair (`â€"` and friends).** Job pages or the model itself occasionally emit UTF-8 punctuation that got decoded as Windows-1252 — a corrupted em-dash/smart-quote. `analyze.py` repairs it with `_fix_mojibake` (guarded cp1252→utf-8 round-trip, no dependency) at three points: `_scrub_html` (fetched text in), the five LLM-output parse sites, and `_get_user_analysis_cache`/`_fix_mojibake_deep` (repairs stale cached rows on read — a cache hit otherwise bypasses output repair). Repair only fires when a marker is present and the round-trip is clean, so legitimate text is never touched. Note: the browser also caches results durably in `localStorage` `pf:analyses:{runId}` (`frontend/src/lib/storage.ts`), so already-viewed cards need that cleared to pick up the repaired data.

- **Microsoft `apply.careers.microsoft.com`** is a search-results SPA, but the page embeds a schema.org JSON-LD `JobPosting` block for Google for Jobs SEO. Handled by `site_handlers/microsoft.py` — no auth, no API, just GET the URL and parse the `<script type="application/ld+json">` block. URLs without a `pid` query param fall through to httpx/Firecrawl.

- **Direct fetch upper bound (`_MAX_CONTENT_LEN = 50_000`)** — Content above 50K chars indicates a search/listing page rather than a standalone job post. This prevents large search pages from being passed to the LLM pipeline.

- **wellfound.com** is Cloudflare-walled (403 to plain clients) and **`jobs.nvidia.com`/SPA career sites** serve only a generic shell server-side — neither gives a cheap liveness signal. `validate_job_url` renders these with Firecrawl (`_firecrawl_job_alive`, proxy `"auto"` — Firecrawl escalates past Cloudflare server-side when blocked, covering both wellfound and SPAs without per-domain proxy selection) and checks the rendered page; a listing is **dropped if Firecrawl can't render it** (network error, empty, or no `FIRECRAWL_API_KEY`). Scrape plumbing is shared in `backend/lib/firecrawl.py`. Trade-off: without a Firecrawl key these domains all drop, thinning the wellfound-heavy startup bucket. _(The deprecated v1 `"stealth"` proxy name was retired in favor of `"auto"`; `FIRECRAWL_TIMEOUT_MS` must stay ≥ 90000 or slow `auto` renders 408 `SCRAPE_TIMEOUT`.)_

- **workatastartup.com** requires browser-like headers. Dead listings return 404 or redirect to ycombinator.com — both detected and dropped.

- **Firecrawl `FIRECRAWL_API_KEY` must be set** for the Firecrawl render path (proxy `"auto"`, which escalates past Cloudflare/JS shells server-side) to work. If missing, analyze.py logs a warning and skips Firecrawl entirely (direct fetch only).

- **Firecrawl has a hard concurrent-scrape cap (free/hobby plan = 2 — `GET /v2/team/queue-status` → `maxConcurrency`), and over-subscribing it causes timeouts + orphaned jobs, NOT just queuing.** The worker fans validation out at `_VALIDATE_CONCURRENCY=10` and company-recovery at `WORKER_PARSE_CONCURRENCY=8`, far above the plan limit. When more scrapes than the cap are in flight, the excess **queue on Firecrawl's side, and queue-wait counts against our client/`timeout` budget** — so a scrape can burn its whole budget waiting in line, our httpx connection drops, Firecrawl abandons the backend job, and the dashboard shows it stuck **"IN PROGRESS" with 0 credits forever** (querying the job id returns `404 Job not found` — it's a stale display record, not a live process; harmless, nothing to cancel). The fix is a per-process semaphore in `lib/firecrawl.scrape()` sized to `FIRECRAWL_MAX_CONCURRENCY` (default 2): it gates **every** caller (worker validation, parse-pass company recovery, `/analyze`, local fallback) at the client boundary. Bounding to the cap costs ~no throughput (Firecrawl is the bottleneck regardless) and eliminates the queue-thrash 408s. Raise the env only after upgrading the plan. (Per-process: worker + each web replica get their own pool, so concurrent worker+web load can briefly hit N×the cap — Firecrawl just queues the small overflow.)

- **The run cache** (`run_cache` table) is live. To disable during development, comment out the `get_run_cache`/`set_run_cache` calls in `run.py`.

- **CORS is localhost-only.** `main.py` allows `http://localhost:3000` only. Update `allow_origins` before deploying.

- **A generic `except Exception` will SWALLOW `HTTPException` into a raw 500.** `fastapi.HTTPException` subclasses `Exception`, so a route that maps friendly errors (e.g. `analyze_profile` raising `HTTPException(503)` for a LinkdAPI 429) will have them re-wrapped as a generic 500 if the caller's `try/except Exception` doesn't re-raise them first. **Every route that wraps extraction must put `except HTTPException: raise` BEFORE the generic `except Exception`** (done in `profile.py`, `run.py`, `resume.py`). Same applies to `ValueError`→422 handlers — order the specific catches before the catch-all. Without this, the Day-4 friendly-error mapping silently regresses to raw 500s.

- **Internship serve freshness depends on the worker's cron cadence.** Serving only returns `listing_store` rows validated within `SERVE_MAX_AGE_HOURS` (default 48h). The ingestion worker (`python -m worker.ingest`, ~6h cadence) is what keeps `last_validated` fresh — if it stops running, national buckets go stale and then empty. There's a safety fallback (`_serve_national_rows` retries an empty national bucket at `SERVE_MAX_AGE_FALLBACK_HOURS`, default 96h) so a single missed cycle degrades to slightly-staler rather than empty, but the durable fix is a reliable scheduler for the worker. Keep `SERVE_MAX_AGE_HOURS` comfortably above the real cadence.

- **Run history persists in `localStorage` (durable), centralized in `frontend/src/lib/storage.ts`.** Runs survive tab close / restart and surface as a "Previous runs" list on the home page. Keys are `pf:`-namespaced (`pf:runs` index, `pf:run:{id}`, `pf:analyses:{id}`, `pf:analysis:{id}`); history is capped at the 10 most recent runs (oldest run + its cached analyses evicted together). Per-browser only — no cross-device sync without backend accounts. (Pre-existing `sessionStorage` data from the old design is simply ignored.)

- **Profile cache has no TTL** — once a LinkedIn URL or text hash is cached, it never expires. Clear the `profile_cache` table (`DELETE FROM profile_cache;`, or `scratch/clear_profile_cache.py` — Postgres-aware, unlike the stale SQLite `clear_cache.py`) to force a fresh fetch. **A bad extraction caches its bad result**, so after fixing extraction you MUST clear this before re-testing the same URL or `/run` serves the stale `UnifiedProfile`.

- **Never feed the raw LinkdAPI JSON to an extractor — flatten it to text first** (`_linkedin_profile_to_text` in `profile.py`). The `/profile/full` payload is ~24k chars pretty-printed, ~2/3 of it image URLs / logos / `multiLocale` dupes / ids, with the real content (experience **descriptions**, skills, certs) deep in the body. The old `json.dumps(raw_profile, indent=2)[:8000]` truncated *before* reaching it — silently dropping skills and 3 of 5 jobs — and a raw JSON blob also makes Sonnet echo/prose-wrap instead of returning clean JSON. The flattener renders only the meaningful fields as resume-like prose (~3k chars), which the prompts extract from cleanly (like the resume path) and which fits the budget whole. Both `analyze_profile`'s identity call AND `extract_rich_fields` consume this text. Experience comes from `data.fullPositions` (≡ `data.position`); skills from `data.skills[].name`; education from `data.educations`. Keep separators ASCII (mojibake on Windows logging).

- **`parse_json_with_context(raw, label, expected_keys=...)` for known-shape outputs.** When a model prose-wraps JSON, the bare recovery returns the **first** decodable `{`/`[` — which can be a small *example* object the model wrote mid-reasoning (this zeroed out `profile-rich`: it grabbed an echoed-input fragment instead of the real answer at the end). Pass `expected_keys` (the top-level keys the real answer must contain) and recovery returns the **largest** value that actually has one of them. Default (no `expected_keys`) keeps the first-match behavior the `internships.py` / `listing_parser.py` callers rely on.

- **Quick and full produce different raw fit_scores** (Haiku gestalt vs deterministic category-weighted math). The full route reconciles its headline (`fit_score` + `verdict.call`) from a cached quick entry when one exists, so the card the user clicked and the detail page show the same numbers. The `category_scores` breakdown on the full view is still derived from per-requirement matches and may not weighted-average exactly to the reconciled headline — accepted trade-off for user-visible consistency.

- **Cache keys depend on a stable `job_id`, not fetched text.** `_compute_job_id(url, text)` returns `"url:<canonical_url>"` when a URL is present and `"text:<sha256(normalized)[:32]>"` otherwise. Same URL across two fetches → same key, even when Firecrawl returns slightly different markdown each time.

- **`uvicorn --reload` (recommended dev command)** auto-restarts on Python file changes. Without `--reload`, edits to backend code require a manual Ctrl-C + restart.

- **`localStorage` `pf:analyses:{runId}`** is what makes return visits to results pages instant. Deleting it (or calling `removeRun`, which also clears it) forces a fresh `/analyze/batch` call (useful if cache key formats change).

- **Old `analysis_cache` SQLite table is orphaned.** When quick mode / batch / per-user caching landed, the canonical store became `user_analysis_cache` (different schema + extra `mode` column). Old rows expire on their existing 24h TTL or can be dropped manually.

- **Roadmap resource URLs go through three guardrails — never trust the LLM's URLs raw** (all in `lib/resource_validation.py`). Stage 0: `_is_generic_url()` rejects search/listing/homepage URLs (e.g. `youtube.com/results?search_query=...`, bare domain roots) — these are live + allowlisted but useless, and Opus 4.8 emits them when it can't recall a specific page. Stage 1: `is_allowlisted()` against the 21-domain frozenset in `config/resource_allowlist.py`. Stage 2: async HEAD with a hard 3 s timeout per URL (retries with `Range: bytes=0-0` GET on 405), results cached 7 days in `url_liveness_cache`. Off-allowlist/generic URLs are dropped without a network call; dead allowlisted URLs are dropped after HEAD fails. `roadmap.txt` forbids search URLs and `RoadmapResource.type` includes `"roadmap"` (Opus 4.8 recommends roadmap.sh paths). The prompt lists the allowlist inline as a hint, but the server is the final authority.

- **Phase 3 failures must not break the analysis response.** `_run_roadmap` and `_run_project_suggestion` are wrapped in try/except inside `_generate_phase3`; any failure logs `[analyze] roadmap generation failed: ...` (or `project_suggestion failed`) and returns `None` for that field. Quick mode is unaffected — `include` flags are ignored for `mode=quick`.

- **Phase 3 cache backfill needs the live request profile.** Older full-mode rows written before Phase 3 don't carry roadmap/project. On a cache hit, `_phase3_backfill_cached_row` rehydrates Phase 3 inputs from the cached row (job_summary/matches/gaps/verdict) plus the live `req.profile` and runs only the missing LLM calls. Without the profile (e.g. a future endpoint that calls backfill out of band), the backfill must be skipped or it will produce low-quality output.

## Always-loaded critical gotchas (full detail; CLAUDE.md carries the one-liners)

- **The Anthropic client + Sonnet rate-limit governor are centralized in `lib/anthropic_client.py`** — every route imports `client as ai` (not its own `anthropic.Anthropic()`), so the raised `max_retries` (SDK exponential backoff w/ jitter honoring `Retry-After`) applies everywhere. **Sonnet (`MODEL_MID`) is the only model that maxes the org's per-minute limits**, so `sonnet_slot()` caps in-flight Sonnet calls to `SONNET_MAX_CONCURRENCY` (default 6) **globally**: wrap **every** Sonnet `messages.create` in `async with sonnet_slot():` in the async layer (around the `to_thread`/`run_in_executor` dispatch — never inside the sync fn) — it's a **factory returning a fresh per-acquire async CM**, NOT a shared semaphore object (the old `sonnet_sem`), so don't store acquire state on one shared singleton. When `REDIS_URL` is set the slot is a **self-healing Redis ZSET semaphore** (held slots TTL-stamped → a crashed replica's slots auto-reclaim; `SONNET_SLOT_TTL_SEC` ≥ `ANTHROPIC_TIMEOUT_SEC`), so the cap is **org-wide across all replicas**; without Redis it degrades to a per-process `asyncio.Semaphore`. **Haiku (batch/results) and Opus (roadmap) stay ungated** (they have headroom). Env knobs: `SONNET_MAX_CONCURRENCY`, `SONNET_SLOT_TTL_SEC`/`_POLL_SEC`/`_MAX_WAIT_SEC`, `ANTHROPIC_MAX_RETRIES`, `REDIS_URL`. **Caveat: without `REDIS_URL` the cap is per-process** — under N replicas the effective global cap becomes N×.

- **`listing_store` keying is `PRIMARY KEY (niche_key, bucket, url)`** — the same URL legitimately lives in multiple contexts (a Stripe listing is big_tech for every field AND in `_reach`). Local rows are keyed by the **`_parse_metro` output** — the worker, serving, and `metro_rotation` must ALL key on parsed metros, never a raw profile location, or covered-metro lookups silently miss.

- **The worker forces UTF-8 stdout** (`sys.stdout.reconfigure`) — as a standalone process with redirected output, Windows defaults to cp1252 and a stray `→`/non-ASCII char in a log line crashes the whole run. Keep that guard.

- **The data layer is Postgres** (`db.py` → `psycopg_pool.ConnectionPool`), shared by uvicorn and the worker; Postgres MVCC handles concurrent read/write (no WAL/sidecar files). **Prod uses the Supabase pgBouncer pooler in transaction mode, so the pool sets `prepare_threshold=None`** (server-side prepared statements break under transaction pooling) — keep that. `cache.py` stays **synchronous**; async routes call it through `asyncio.to_thread` (same discipline as the synchronous Anthropic SDK) so a DB round-trip never blocks the event loop. Schema lives in `alembic/`, not `init_db()`.

- **`MODEL_MID` (Sonnet) sometimes wraps JSON answers in reasoning prose** (`"Looking at the listings:…"` then the array), despite "respond with ONLY JSON" — which breaks a plain `json.loads`. `internships.py`'s shared `_parse_json_with_context` falls back to `_extract_json_value` (scans for the first `[`/`{` that `raw_decode`s) to recover it; reuse that path for any new Sonnet JSON call rather than `json.loads` directly.

- **The quick-verdict prompt (`prompts/quick_verdict.txt`) is no longer a bare rubric** — it carries an **eligibility-gates rule** (date-independent gates like exact major → hard `skip`; time-relative gates like "completed junior year" → only gate on an *explicit* year in the posting, never guess from the current date) + **4 calibration anchors** (same candidate, four jobs: 78/74/60/50). Scoring-behavior tuning for quick/batch lives here. It's ~1900 tokens (was ~280); the larger stable prefix also helps batch profile-caching clear Haiku's 4096-token cache minimum.

- **`[cost]` logging mirrors `[timing]`** — `cost_session`/`record_usage` (`lib/cost.py`) wrap `/analyze` + `/analyze/batch` + `/internships/annotate` **and `/run` + `/profile/analyze` + `/profile/from-resume` + `/connections/suggest`** (the profile-extraction Sonnet + connections Opus calls were previously untracked — `profile.py`/`connections.py` now call `record_usage`, so the ledger is complete) and print est-USD per Claude call + a sorted breakdown. Token counts are exact; **USD is approximate** (price table in `cost.py` — update it if pricing changes). Watch `cache_r` to confirm batch profile-caching is engaging. Every call also **persists to the `cost_events` ledger**, and `record_cache_hit(label, model)` logs a full-call cache avoidance (annotate + batch-quick hits, est-USD saved from `_HIT_ESTIMATE`) — both surfaced via `GET /cost/summary`. _(Adding a new cache-hit type? add its label to `_HIT_ESTIMATE` or savings show as $0.)_ **The worker's Haiku listing-parse is tracked too**: `lib/listing_parser.parse_listing_sync` calls `record_usage("listing-parse", …)` at the shared call site, so it lands in the ledger under whatever `cost_session` is active — `worker:ingest` for the worker parse pass, or the request session (`/run`, `/internships/search`) for the local live-fetch fallback. **`worker:%`-tagged spend is EXCLUDED from the kill switch's `sum_spend_since`** (it has its own `WORKER_SPEND_CAP_USD_DAILY`); request-tagged + NULL-session spend still counts.

- **Reliability hardening (Day 4):** bad input maps to friendly statuses, not raw 500s — `analyze_profile` (`profile.py`) translates LinkdAPI `httpx.HTTPStatusError`/`RequestError` (404/private→422, 429→503, 5xx→502, timeout→504) and guards short pastes; **a global `@app.exception_handler(Exception)` in `main.py`** is the backstop (logs `[error]` + traceback, returns a clean 500, has a `# SENTRY:` hook — Sentry deferred). **Critical: routes wrapping extraction must `except HTTPException: raise` before the generic `except`** or the friendly errors regress to 500s. Timeouts/retries added: Anthropic request `timeout` (`ANTHROPIC_TIMEOUT_SEC`), LinkdAPI transient retries (`linkd.py`), per-query DDG `wait_for` in the worker (`ingest_core.py`), one Firecrawl network retry. `_select_and_build` isolates each card build (one malformed `listing_store` row can't break a bucket). Serve freshness tightened to `SERVE_MAX_AGE_HOURS` (48h) with an empty-national-bucket fallback to `SERVE_MAX_AGE_FALLBACK_HOURS` (96h) — depends on the worker's cron cadence.

- **Cost-protection gate (`lib/guard.py`) is a per-router dependency, NOT middleware** — `cost_guard` is attached via `dependencies=[Depends(cost_guard)]` on the LLM-firing routers in `main.py` (deliberately a `yield`-dependency, not `BaseHTTPMiddleware`, which would buffer/break the ndjson `StreamingResponse` of `/analyze/batch` + `/internships/annotate`; dependency teardown runs after the stream, so the per-IP concurrent counter releases correctly). It enforces per-IP rate + concurrency caps (`429`) and a kill switch (`503`: auto when rolling spend ≥ `SPEND_CAP_USD_DAILY`, or the manual persistent `app_flags.kill_switch` toggled via `POST /admin/killswitch`). **State is Redis-backed (shared across replicas) when `REDIS_URL` is set, else in-process / per-replica.** The per-IP limiter is an atomic Lua reserve over two ZSETs (sliding-window rate + crash-TTL'd concurrency, `RATE_LIMIT_INFLIGHT_TTL_SEC`); the rolling spend total is a shared Redis cache key with an in-process throttle on the Postgres `SUM`. The manual kill-switch flag stays in **Postgres `app_flags`** (must survive restart + toggle instantly). All three paths **fall back to the original in-process implementation** when Redis is absent/unhealthy — local dev needs no Redis, and a Redis outage degrades to per-replica limiting (looser, never tighter), not a 503. `lib/redis_client.py` is the shared async client + a **circuit breaker** (`REDIS_RETRY_COOLDOWN_SEC`) so a dead Redis trips fast instead of timing out every request. `/cost/summary`, `/admin/*`, `/health` are ungated on purpose. Both spend-cap and flag reads **fail open** (a DB/Redis hiccup must not 503 all traffic).

- **The results page dedupes internships by `application_url` before batch scoring** (`frontend/src/app/results/[id]/page.tsx`) — the same listing can sit in multiple buckets (big_tech AND reach), so each URL is scored **once** and the verdict fanned out to every slot that shares it. Scoring is per `(profile, job)` and bucket-independent.

- **The annotation ("why you fit") is lazy, the score badge is eager** — `InternshipCard` is a click-to-expand accordion; expanding a card fires a **single-role** `/internships/annotate` call on first open (not on page load), guarded by `annotateRequestedRef` so it never refetches, and fanned to every slot sharing the URL. It caches client-side (localStorage) and server-side (`annotate_cache`). Score badges still batch-score on load. See [frontend.md](frontend.md).

- **Voyage embeddings (`lib/embeddings.py`) are optional + have operational quirks.** (1) **Anthropic has no embeddings API** — embeddings are Voyage (`VOYAGE_API_KEY`); the wrapper is import-guarded so a missing `voyageai` package / key never crashes a route (`is_available()` → False → serving skips cosine ranking, worker stores parses without vectors). (2) **Free tier needs a payment method** — without one Voyage caps at **3 RPM / 10K TPM**, which is too small for even one 128-doc batch (it 408/429s the whole `embed_documents` call); adding a card unlocks real limits and the 200M voyage-3 free tokens still apply, so it stays effectively free. (3) **Vectors are normalized at store + query time** so serve-time cosine == dot product; **changing `EMBED_MODEL` orphans existing vectors** (serving only cosine-matches the same `embedding_model`+`embedding_dim`; mismatches fall to unranked) and `content_hash` does NOT fire on a model swap — reset with `UPDATE listing_store SET parsed_at=NULL`.

- **When fixing URL/listing validation for internship buckets, verify against the ACTUAL page title and real listings — not DDG search titles or minified SPA JS — and confirm the fix returns >0 live roles before declaring done.** _(Multiple bucket/category fixes — startup, local, big_tech, reach, category landing page — repeatedly returned 0 results because validation matched the wrong source; one over-aggressive `CLOSED_STRINGS` match against minified SPA JS deleted every startup role and forced a revert.)_

- **After modifying caching logic, confirm quick and full modes share consistent cache keys and that the backend was actually restarted before testing.** _(A score-mismatch fix failed repeatedly because quick and full modes used divergent cache keys, compounded by confusion over whether the backend had restarted.)_
