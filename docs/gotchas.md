# Known constraints and gotchas

- **`ai.messages.create` is synchronous.** Always wrap in `asyncio.to_thread()` when running alongside other async work. Calling it directly in an `async def` blocks the entire event loop. In `/run`, connections and internships run in parallel via `asyncio.gather`, so a blocking Claude call in one branch freezes the other — `connections.py`'s Claude call is wrapped in `asyncio.to_thread` for exactly this reason (it had been a blocking call).

- **DDGS is synchronous and not thread-safe.** Each `asyncio.to_thread` call using DDGS must instantiate its own `DDGS()` object. Calling `DDGS().text()` directly in an `async def` blocks the event loop AND can hang for minutes when DDG rate-limits (common late in a `/run`, after the bucket scrapes already hit DDG). Reach URL-finding (`_find_job_url`, `_find_via_startup_boards`) runs its DDG work in a thread bounded by `asyncio.wait_for(timeout=_DDG_URL_TIMEOUT=15)` — on timeout the item gets no URL and is dropped downstream (graceful degradation).

- **Opus 4.8 rejects `temperature`/`top_p`/`top_k`** (400 `temperature is deprecated for this model`). All `MODEL_FULL` calls in `analyze.py` had `temperature` removed during the 4.5→4.8 migration; the Haiku quick-verdict call still passes `temperature` (Haiku accepts it). Do not add sampling params to Opus calls.

- **`max_tokens` truncation surfaces as "retry".** Opus 4.8 runs longer than 4.5, and a too-low `max_tokens` cuts the JSON mid-output → `json.loads` fails → the card shows a "retry" badge. In `analyze.py`: extraction is **2048** (was 1024 — Amazon's 18-requirement posting overflowed it), roadmap **4096**, evidence 2048. `internships.py` serving is zero-LLM; the only Claude call is the deferred `_annotate_fit_sync` behind `/internships/annotate`, which emits just `{fit_explanation, reach_gap}` (`max_tokens=160`; `fit_explanation` ~2 sentences / ~30 words, `reach_gap` ~25 words for a scannable shortlist + faster generation). If you add longer explanation text, bump the 160.
- **The internships annotation fan-out is input-token-heavy — mind the org's per-minute limits.** The fan-out no longer runs in `search_internships` (that path is zero-LLM) — it moved to `POST /internships/annotate`, which the results page fires *after* the feed paints, one small Claude call per served role (~up to 20 deduped URLs). On a low tier (e.g. 30k input-tokens/min, 50 req/min) the burst grazes the limit. Two guards keep it working and must stay: (1) `_profile_brief(profile)` sends a terse profile, NOT `model_dump(indent=2)` — the full dump re-sent per role blows the input-TPM limit; (2) the shared client is `anthropic.Anthropic(max_retries=…)` so 429s recover (slower) instead of dropping roles. In-flight calls are bounded by the process-wide `sonnet_sem`; if you re-add big per-call input, re-check against the tier limits.

- **Mojibake repair (`â€"` and friends).** Job pages or the model itself occasionally emit UTF-8 punctuation that got decoded as Windows-1252 — a corrupted em-dash/smart-quote. `analyze.py` repairs it with `_fix_mojibake` (guarded cp1252→utf-8 round-trip, no dependency) at three points: `_scrub_html` (fetched text in), the five LLM-output parse sites, and `_get_user_analysis_cache`/`_fix_mojibake_deep` (repairs stale cached rows on read — a cache hit otherwise bypasses output repair). Repair only fires when a marker is present and the round-trip is clean, so legitimate text is never touched. Note: the browser also caches results durably in `localStorage` `pf:analyses:{runId}` (`frontend/src/lib/storage.ts`), so already-viewed cards need that cleared to pick up the repaired data.

- **Microsoft `apply.careers.microsoft.com`** is a search-results SPA, but the page embeds a schema.org JSON-LD `JobPosting` block for Google for Jobs SEO. Handled by `site_handlers/microsoft.py` — no auth, no API, just GET the URL and parse the `<script type="application/ld+json">` block. URLs without a `pid` query param fall through to httpx/Firecrawl.

- **Direct fetch upper bound (`_MAX_CONTENT_LEN = 50_000`)** — Content above 50K chars indicates a search/listing page rather than a standalone job post. This prevents large search pages from being passed to the LLM pipeline.

- **wellfound.com** is Cloudflare-walled (403 to plain clients) and **`jobs.nvidia.com`/SPA career sites** serve only a generic shell server-side — neither gives a cheap liveness signal. `validate_job_url` renders these with Firecrawl (`_firecrawl_job_alive` — stealth for wellfound, basic for SPAs) and checks the rendered page; a listing is **dropped if Firecrawl can't render it** (network error, empty, or no `FIRECRAWL_API_KEY`). Scrape plumbing is shared in `backend/lib/firecrawl.py`. Trade-off: without a Firecrawl key these domains all drop, thinning the wellfound-heavy startup bucket.

- **workatastartup.com** requires browser-like headers. Dead listings return 404 or redirect to ycombinator.com — both detected and dropped.

- **Firecrawl `FIRECRAWL_API_KEY` must be set** for the stealth escalation path to work. If missing, analyze.py logs a warning and skips Firecrawl entirely (direct fetch only).

- **The run cache** (`run_cache` table) is live. To disable during development, comment out the `get_run_cache`/`set_run_cache` calls in `run.py`.

- **CORS is localhost-only.** `main.py` allows `http://localhost:3000` only. Update `allow_origins` before deploying.

- **A generic `except Exception` will SWALLOW `HTTPException` into a raw 500.** `fastapi.HTTPException` subclasses `Exception`, so a route that maps friendly errors (e.g. `analyze_profile` raising `HTTPException(503)` for a LinkdAPI 429) will have them re-wrapped as a generic 500 if the caller's `try/except Exception` doesn't re-raise them first. **Every route that wraps extraction must put `except HTTPException: raise` BEFORE the generic `except Exception`** (done in `profile.py`, `run.py`, `resume.py`). Same applies to `ValueError`→422 handlers — order the specific catches before the catch-all. Without this, the Day-4 friendly-error mapping silently regresses to raw 500s.

- **Internship serve freshness depends on the worker's cron cadence.** Serving only returns `listing_store` rows validated within `SERVE_MAX_AGE_HOURS` (default 48h). The ingestion worker (`python -m worker.ingest`, ~6h cadence) is what keeps `last_validated` fresh — if it stops running, national buckets go stale and then empty. There's a safety fallback (`_serve_national_rows` retries an empty national bucket at `SERVE_MAX_AGE_FALLBACK_HOURS`, default 96h) so a single missed cycle degrades to slightly-staler rather than empty, but the durable fix is a reliable scheduler for the worker. Keep `SERVE_MAX_AGE_HOURS` comfortably above the real cadence.

- **Run history persists in `localStorage` (durable), centralized in `frontend/src/lib/storage.ts`.** Runs survive tab close / restart and surface as a "Previous runs" list on the home page. Keys are `pf:`-namespaced (`pf:runs` index, `pf:run:{id}`, `pf:analyses:{id}`, `pf:analysis:{id}`); history is capped at the 10 most recent runs (oldest run + its cached analyses evicted together). Per-browser only — no cross-device sync without backend accounts. (Pre-existing `sessionStorage` data from the old design is simply ignored.)

- **Profile cache has no TTL** — once a LinkedIn URL or text hash is cached, it never expires. Delete `pathfinder_cache.db` or clear `profile_cache` table to force a fresh fetch.

- **Quick and full produce different raw fit_scores** (Haiku gestalt vs deterministic category-weighted math). The full route reconciles its headline (`fit_score` + `verdict.call`) from a cached quick entry when one exists, so the card the user clicked and the detail page show the same numbers. The `category_scores` breakdown on the full view is still derived from per-requirement matches and may not weighted-average exactly to the reconciled headline — accepted trade-off for user-visible consistency.

- **Cache keys depend on a stable `job_id`, not fetched text.** `_compute_job_id(url, text)` returns `"url:<canonical_url>"` when a URL is present and `"text:<sha256(normalized)[:32]>"` otherwise. Same URL across two fetches → same key, even when Firecrawl returns slightly different markdown each time.

- **`uvicorn --reload` (recommended dev command)** auto-restarts on Python file changes. Without `--reload`, edits to backend code require a manual Ctrl-C + restart.

- **`localStorage` `pf:analyses:{runId}`** is what makes return visits to results pages instant. Deleting it (or calling `removeRun`, which also clears it) forces a fresh `/analyze/batch` call (useful if cache key formats change).

- **Old `analysis_cache` SQLite table is orphaned.** When quick mode / batch / per-user caching landed, the canonical store became `user_analysis_cache` (different schema + extra `mode` column). Old rows expire on their existing 24h TTL or can be dropped manually.

- **Roadmap resource URLs go through three guardrails — never trust the LLM's URLs raw** (all in `lib/resource_validation.py`). Stage 0: `_is_generic_url()` rejects search/listing/homepage URLs (e.g. `youtube.com/results?search_query=...`, bare domain roots) — these are live + allowlisted but useless, and Opus 4.8 emits them when it can't recall a specific page. Stage 1: `is_allowlisted()` against the 21-domain frozenset in `config/resource_allowlist.py`. Stage 2: async HEAD with a hard 3 s timeout per URL (retries with `Range: bytes=0-0` GET on 405), results cached 7 days in `url_liveness_cache`. Off-allowlist/generic URLs are dropped without a network call; dead allowlisted URLs are dropped after HEAD fails. `roadmap.txt` forbids search URLs and `RoadmapResource.type` includes `"roadmap"` (Opus 4.8 recommends roadmap.sh paths). The prompt lists the allowlist inline as a hint, but the server is the final authority.

- **Phase 3 failures must not break the analysis response.** `_run_roadmap` and `_run_project_suggestion` are wrapped in try/except inside `_generate_phase3`; any failure logs `[analyze] roadmap generation failed: ...` (or `project_suggestion failed`) and returns `None` for that field. Quick mode is unaffected — `include` flags are ignored for `mode=quick`.

- **Phase 3 cache backfill needs the live request profile.** Older full-mode rows written before Phase 3 don't carry roadmap/project. On a cache hit, `_phase3_backfill_cached_row` rehydrates Phase 3 inputs from the cached row (job_summary/matches/gaps/verdict) plus the live `req.profile` and runs only the missing LLM calls. Without the profile (e.g. a future endpoint that calls backfill out of band), the backfill must be skipped or it will produce low-quality output.
